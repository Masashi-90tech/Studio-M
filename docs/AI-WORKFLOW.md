# AI との開発の進め方: 司令塔は Opus、実行役は Sonnet と Haiku

2026-11-13 に決めた。目的は、使用量（トークン）を無駄にせずに、設計の質を保つことである。

## 役割

| 役 | モデル | 受け持つこと | 定義 |
|---|---|---|---|
| 司令塔（メインの会話） | Opus | 方針と設計、作業の分割、指示書づくり、差分のレビュー、コミットとプルリクエスト | セッションのモデルを `opus` にする |
| 実装役 `implementer` | Sonnet | 指示書 1 つぶんの実装とテスト、`npm run check` | `.claude/agents/implementer.md` |
| 確認役 `checker` | Haiku | `npm run check` などを実行し、失敗の要点だけを返す。ファイルは書き換えない | `.claude/agents/checker.md` |
| 調査役 `Explore` | Haiku | コードの場所探し（読むだけ） | `.claude/agents/explore.md` |

`Explore` は Claude Code に最初からある調査役と同じ名前にしてある。同じ名前のプロジェクトの定義は、組み込みのものより優先されるので、組み込みの調査役も Haiku で動くようになる（公式ドキュメントによる）。

実行役のモデルは、定義ファイルの `model:` で固定している。司令塔のモデルを `/model` で切り替えても、実行役のモデルは変わらない。

## 使用量を抑えるための約束

実行役は会話の履歴を見られないので、渡された指示書と `CLAUDE.md` を読んで、ゼロから作業を始める。仕事を渡すたびに、指示書を書く手間と、実行役がファイルを読み直す分の使用量がかかる。そのため、渡す仕事は大きさで選ぶ。

1. 数行で済む修正や 1 ファイルだけの修正は、司令塔がそのまま直す。実行役に渡すと、かえって高くつく
2. まとまった実装（複数のファイル、テストの追加を含むもの）は実装役に渡す
3. 指示書には、目的、触るファイル、守る約束（`CLAUDE.md` の該当部分）、完了の条件、報告の形を書く。実行役が自分で調べ直す量を減らすためである
4. 実行役は同時に 1 つ、多くても 2 つまでにする。並列にすると、その数だけ使用量が増える
5. 報告は短くしてもらう。変えたファイル、`npm run check` の結果、迷った点だけで、ログの全文は返さない
6. 司令塔は `git diff` で差分を見てレビューする。ファイル全体を読み直さない
7. 実装役が 2 回続けて同じところで失敗したら、司令塔が引き取る
8. 版や実証実験の区切りごとに、新しいセッションを始める。引き継ぐことは `docs/` に書いておく。会話が長くなるほど、1 回のやり取りで読む量が増えるためである

`CLAUDE.md` は、司令塔にも実行役にも毎回読み込まれる。長くすると、すべてのやり取りで読む量が増えるので、詳しい説明は `docs/` に置き、`CLAUDE.md` には約束だけを書く。

## モデルの切り替え方

- 司令塔を Opus にする: セッションの中で `/model opus`、または起動時に `claude --model opus`
- 計画のあいだだけ Opus にし、実装は Sonnet で進める組み込みの設定もある: `/model opusplan`（計画モードのときは Opus、それ以外は Sonnet）。司令塔と実装役を分けずに 1 つの会話で進めたいときに使う
- 実行役の定義（モデルを含む）は `/agents` で確かめられる。過去の版の Claude Code には、`model:` の指定が無視され、実行役が司令塔と同じモデルで動いたという報告があった。使用量の減り方がおかしいと感じたら、Claude Code を更新してから確かめる

## 公開されているスキルとの関係

GitHub で公開されている仕組みを 2026-11-13 に調べた。どれも MIT ライセンスである。今は入れず、上の公式の仕組み（サブエージェントの定義と `model:` の指定）だけで進める。理由は、大きな仕組みを入れると、そのスキルや指示が毎回読み込まれ、それ自体が使用量を増やすためである。

| 名前 | 中身 | 判断 |
|---|---|---|
| [obra/superpowers](https://github.com/obra/superpowers) | 計画を書く → サブエージェントに 1 つずつ実装させる → 仕様と品質の 2 段階でレビューする、という進め方のスキル集。スター 31.7 万 | 進め方の参考にする。モデルの使い分けは扱っていない。入れるなら `subagent-driven-development` と `writing-plans` だけを試す |
| [wshobson/agents](https://github.com/wshobson/agents) | 202 個のエージェントと 185 個のスキルを集めたもの。エージェントごとに `model:` を指定している | 定義の書き方の参考にする。数が多いので丸ごとは入れない |
| [Yeachan-Heo/oh-my-claudecode](https://github.com/Yeachan-Heo/oh-my-claudecode) | Haiku と Opus を自動で使い分ける、複数エージェントの仕組み。「使用量を 30〜50% 減らす」とあるが、測り方は書かれていない | 見送る。設定ファイルやフックを書き換える大きな仕組みで、Studio M の規模には大きすぎる |
| [akaCT/conductor](https://github.com/akaCT/conductor) | 司令塔が計画し、Sonnet と Haiku に固定した実行役に仕事を渡す仕組み。考え方は今回の分担とほぼ同じ | 見送る。版は 0.3.0 で、スターもまだ付いていない。インストーラーが `CLAUDE.md` を書き換える |
